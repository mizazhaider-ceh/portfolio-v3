## 6. What is worth preserving, and what must go

### 6.1 Preserve (engineering, not design)

- **Routing and app shell:** `BrowserRouter`, the 17-route table in `App.tsx`, shared Nav plus main plus Footer shell, `ScrollToTop`, catch-all 404 route. The route set itself is sound; only the visuals change.
- **Data model:** `src/data.ts` as the single typed content source. Keep the structure and the verification discipline (every fact traceable to the content model). Re-verify the facts against `research/CONTENT-MODEL.md` before reuse; do not retype from memory. Note the open content items in Section 5.
- **Build:** `tsc -b && vite build`, strict TypeScript, Vite plus React plus Tailwind 4 plugin setup, `vite.config.ts` as is. The build is small and fast (see Section 8).
- **SEO:** per-page `usePageMeta` (title, description, canonical, Open Graph, Twitter, per-page JSON-LD), home Person JSON-LD in `index.html`, `sitemap.xml` (16 URLs), `robots.txt`, meta description and keywords, canonical link. Keep the mechanism; rewrite the copy only where the rebuild changes it.
- **SPA fallback:** `vercel.json` rewrite plus `public/_redirects`. Keep both.
- **Static 404:** `public/404.html` as a host-level fallback. Keep the file; restyle it with the new design system.
- **Diagram embeds:** `DiagramFigure` embed pattern (`?embed=1`, theme query param synced live by `MutationObserver`, captioned figure, "Open the diagram" fallback link). Keep the mechanism; the three diagram HTML files themselves are content and can be reused if the rebuild keeps them, but their internal styling must be checked against the new design (they are self-contained Archify viewer pages).
- **Theme persistence mechanism:** pre-paint script in `index.html` plus `useTheme` reading and writing one localStorage key and the `data-theme` attribute, with `meta theme-color` sync. Keep the mechanism and the key name `portfolio-v2-theme` unless the rebuild deliberately renames it (renaming logs every returning visitor out of their saved theme). Only the token values change.
- **Form wiring:** `ContactForm` validation, inline errors, aria wiring, and idle, sending, sent, and error states, posting to the Formspree endpoint in `CONTACT.formspree`. Keep the behaviour; restyle the inputs.
- **Accessibility bones:** skip link, `aria-label` on every section, focus-visible ring, `aria-invalid` and `aria-describedby` on form fields, `aria-pressed` on theme and filter controls, `role="dialog"` and `aria-modal` on the lightbox, `alt` text and explicit width and height on images, reduced-motion fallbacks (tagline, entrance animation, global duration clamp). Keep and extend; see gaps in Section 7.
- **Self-hosted fonts:** Sora and Inter WOFF2 in `public/fonts/`, `font-display: swap`, no external requests. Keep the files unless the new design picks different typefaces.
- **Proof assets:** all 10 images and the sanitized CV PDF. Keep the files; optimise the PNGs (see Section 7).
- **Hooks:** `useCopy` (2-second Copied state), `usePageMeta`, `useTheme`. Keep as is, apart from theme values.
- **CodeStrip highlighter:** the tokeniser and its colour mapping are a reusable mechanism. Keep the code, re-map the token colours to the new design system.

## 7. Existing weaknesses (blockers and risks for the rebuild)

1. **Oversized assets, no optimisation pipeline.** `public/` is 6.7 MB. The largest files are `yeswehack-swag.png` (1.5 MB), the three diagram HTML files (820-852 KB each, 2.5 MB total, mostly embedded base64 font data), `profile.png` (806 KB), and `cscb-rankings.png` (458 KB). There is no image optimisation, no responsive `srcset`, no AVIF or WebP, no compression step in the build. The built `dist/` is 7.1 MB. The rebuild should compress the PNG screenshots, consider WebP or AVIF with PNG fallback, and check whether the diagrams can share one font payload instead of embedding it three times.
2. **Hero image is lazy-loaded.** `profile.png` has `loading="lazy"` on both Home and About, where it sits above the fold. That delays the largest contentful paint image. It should be eager (and ideally `fetchpriority="high"`) on Home and About. The same lazy-load timing caused false-positive "bad image" flags in the v2 sweep (checker read `img.complete` before lazy images started).
